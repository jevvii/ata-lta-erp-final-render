1. Executive Summary & Authorization Architecture

This document establishes the definitive, system-wide Role-Based Access Control (RBAC), Multi-Tenant Scoping, and Record-Level View Permissions Matrix for the ATA & LTA Enterprise Resource Planning (ERP) platform. The platform is designed specifically for dual accounting entities—Alliance Tax & Accounting (ATA) and Ledger Tax & Accounting (LTA)—to deliver end-to-end management of client onboarding, work request workflows, task tracking, accounts receivable (billing), accounts payable (disbursements), document custody (DMS), transmittals, operational requests, and regulatory compliance reporting.

1.1 The Dual-Tier Operational Architecture & Universal Dual Scoping

The platform strictly bifurcates system actors into two operational tiers, ensuring high-level executive governance while maintaining data encapsulation across field personnel. A core architectural principle of the ATA & LTA ERP is that all user roles can be assigned dual-entity scope (['ATA', 'LTA']):

1. Managerial & Oversight Tier:  Comprises the System Administrator (Admin) and General Managers (Manager / Management department). Designed for strategic firm-wide oversight, cross-entity performance monitoring, executive analytics, financial release approvals, phase routing authorization, and exception dispute resolution. Managerial users with dual-entity access possess the privilege to view aggregated multi-tenant data via the Consolidated Firm View ('ALL').

2. Execution & Staff Tier:  Comprises Accounting, Operations, Documentation, and Human Resources (HR) specialists. Designed for daily operational task execution under strict data encapsulation. All staff roles can be configured with dual-entity access (['ATA', 'LTA']) or single-entity access (['ATA'] or ['LTA']). When granted dual-entity access, staff members can switch active workspace between ATA and LTA at will to execute duties across both entities, while maintaining complete data separation between the two tenant databases.

1.2 The Hybrid RBAC Engine

The authorization engine operates as a hybrid intersection of two primary database-driven concepts defined in backend/src/lib/permissions.js and mirrored on the client in erp_prototype/js/auth.js:

• Primary System Role:  Stored in the 'users.role' column (Admin, Manager, Accounting, Operations, Documentation, HR). Identifies user persona, default navigation layout, and fallback department association.

• Department Membership Allowlist:  Stored in the normalized 'user_departments' junction table referencing the 'departments' table (Management, Accounting, Operations, Documentation, HR). Department assignments dictate granular functional capabilities.

• Effective Permissions Union:  A user's effective permission set is computed as the mathematical union of all permissions granted across all assigned departments, plus the primary role mapped to its department equivalent (e.g., role 'Manager' maps to 'Management').

• Administrator Superuser Override:  A user possessing the 'Admin' role automatically bypasses individual department assignment checks and receives the superset of all department permissions, in addition to exclusive system administrative capabilities (users:manage, clients:edit, transmittal:approve, bypass_review:*, approve_change:*).

1.3 Five-Layer Defense-in-Depth Authorization Stack

Security enforcement is implemented across five discrete layers to ensure zero-trust verification on every request:

1. Authentication Gateway (middleware/auth.js):  Verifies Supabase Bearer JWT tokens. Loads internal ERP profiles and active status. Caches user profiles in Node.js memory for 5 minutes (PROFILE_CACHE_TTL_MS = 300,000) with a 500-entry capacity cap.

2. Multi-Tenant Scoping Gateway (middleware/entityScope.js):  Inspects the 'X-Active-Entity' HTTP header. Validates tenant access against user's permitted entities ('ATA', 'LTA'). Validates that consolidated view ('ALL') is restricted solely to managerial users with dual-entity grants.

3. Route-Level RBAC Guards (middleware/rbac.js):  Middleware factory evaluating required permissions (e.g., 'clients:view', 'disbursement:create') against the user's computed effective permission set. Supports wildcard matches (e.g., 'approve_change:*').

4. Database Stored Procedure Gates (PostgreSQL RPCs):  State-machine transitions (e.g., invoice_record_payment, disbursement_transition, pending_change_approve) are enforced via PostgreSQL PL/pgSQL functions executing under ACID row-level locks.

5. Reactive Frontend UI Engine (erp_prototype/js):  Client-side authorization service (Auth.can, Auth.isManagerial) dynamically renders UI navigation, enables/disables action buttons, filters sensitive table columns, and prevents unauthorized DOM interactions.

2.1 Granular Role Profiles & Segregation of Duties

The ATA & LTA ERP enforces strict segregation of duties to satisfy statutory auditability, professional standards, and operational risk mitigation:

1. Administrator (Admin):  Holds full administrative authority across all twelve modules. Responsible for provisioning accounts, assigning departments, configuring entity access (dual or single), and reviewing audit trails. Bypasses all review gates directly.

2. General Manager (Manager):  Manages end-to-end client engagements. Can be assigned dual entity scope to monitor both ATA and LTA, or single entity. Creates work requests (which stage for Admin approval). Approves tasks submitted by staff. Monitors team time logs. Can request invoices from Accounting and request disbursements. Can mark invoices as paid and disbursements as released (subject to Admin approval). Cannot edit or create financial records directly.

3. Senior Accountant (Accounting):  Dedicated financial controller. Can be assigned dual entity scope to manage finances for both ATA and LTA, or single entity. Possesses exclusive authority to generate invoices, apply line items, record client payments, manage retainer billing templates, and file disbursement expense requests. Acts as an independent review authority for invoice and disbursement modifications submitted by other staff.

4. Operations Specialist (Operations):  Direct operational executor. Can be assigned dual entity scope to handle operational permits and compliance for both ATA and LTA clients, or single entity. Completes task checklists, uploads verification documents, logs worker hours, and flags task dependencies. Submits official operations requests when billing or disbursement funds are required for field execution.

5. Documentation Officer (Documentation):  Manages official client and agency documentation. Frequently assigned dual entity scope to maintain document custody across both firms. Generates transmittal records for document release and tracks courier delivery acknowledgments. Manages document lifecycle states (collected -> active -> transmitted -> inactive).

6. Human Resources Specialist (HR):  Human resource administrative officer. Can be assigned dual entity scope to oversee workforce management for both firms, or single entity. Monitors staff allocation, reviews task time logs for workforce productivity, initiates inter-departmental operations requests, and reviews monthly pending workflow analytics.

3. Multi-Tenant Entity Access Scoping Matrix

The ATA & LTA platform implements a multi-tenant data isolation model within a unified PostgreSQL database. Tenant separation is enforced via the 'entities' array on user profiles and the 'entity' / 'entity_id' column on database tables.

3.1 Universal Dual-Entity Capability

A foundational architectural capability of the platform is that all user roles—regardless of operational tier—can be provisioned with dual-entity scope (entities = ARRAY['ATA', 'LTA']):

• Flexible Configuration:  The database schema ('users.entities text[]') and administrative user endpoints (/v1/admin/users) enforce no restriction on entity assignments by role. Any employee in Accounting, Operations, Documentation, HR, Management, or Administration can be assigned to 'ATA' only, 'LTA' only, or both 'ATA' and 'LTA'.

• Discrete Context Switching:  Any user assigned both entities is automatically provided the entity switcher dropdown in the navigation shell. Switching active entity dynamically sets the 'X-Active-Entity' header and re-scopes the entire client workspace, API queries, caches, and form selectors.

• Consolidated ('ALL') vs Discrete Switching:  While dual-entity staff can switch between ATA and LTA discretely to execute work in either firm, accessing the aggregated Consolidated Firm View ('ALL') is restricted to managerial users. Staff members manage each entity's records independently to preserve clean accounting and audit ledgers.

3.2 Scoping Gateway & The 'ALL' Consolidated View Rules

Tenant scoping is evaluated by backend/src/middleware/entityScope.js on every authenticated HTTP request via the 'X-Active-Entity' header. Strict enforcement rules apply:

1. Automatic Resolution:  If the client omits 'X-Active-Entity' or sends an invalid entity, the system automatically resolves to the user's first assigned entity. If the user has no valid assigned entity, the request is rejected with 400 Bad Request.

2. Single-Tenant Isolation:  Single-entity users assigned only to 'ATA' or 'LTA' can never access data belonging to the other entity. Requesting an unassigned entity triggers an immediate 403 Forbidden error.

3. Consolidated View ('ALL') Prerequisites:  Requesting 'ALL' requires the user to satisfy TWO mandatory prerequisites: (a) The user must hold a managerial role ('Admin', 'Manager', or 'Management' department), AND (b) The user must have explicit access to both 'ATA' and 'LTA' in their 'entities' array. If either condition is unmet, the gateway returns 403 Forbidden ('Consolidated view requires a managerial role' or 'Consolidated view requires access to both ATA and LTA entities').

5. Record-Level View Scoping & Data Encapsulation

In addition to module-level route guards, the platform implements granular row-level data encapsulation. This ensures that staff members only interact with records directly relevant to their assigned duties, mitigating unauthorized visibility into sensitive client billing, overhead expenses, and unrelated legal casework.

5.1 Work Request Visibility Engine (canViewWr & canViewWrWithTasks)

When a user queries work requests via the API (/v1/work-requests) or navigates the Kanban board in the frontend client, record visibility is filtered using the following deterministic logic (erp_prototype/js/auth.js):

1. Administrator:  User can view all work requests within their active entity scope without restriction.

2. Managerial Users (Manager / Management dept):  User can view a work request IF AND ONLY IF they are the submitter (wr.submittedBy === user.id) OR the designated requester (wr.requestedBy === user.id). Unrelated work requests managed by other personnel remain invisible.

3. Staff-Level Users (Accounting, Operations, Documentation, HR):  A work request card is rendered IF AND ONLY IF the user is explicitly assigned to at least one task or checklist item within that work request. The engine checks: (a) task.assigneeId === user.id, (b) task.assignedTo === user.id, (c) task.assigneeName === user.name, (d) task.coAssignees includes user.name, or (e) task.checklist item assigneeName === user.name. If no task matches, the entire work request card and its timeline are concealed.

5.2 Financial Records Visibility Engine (Disbursements & Billing)

• Disbursement Scoping (canViewDisbursement):  Admin and Accounting personnel can view all disbursement records within their assigned active entity. Managerial users can view disbursements linked to work requests they own or disbursements they personally requested. Staff users can only view disbursements linked to work requests they are assigned to, disbursements they personally requested, or records that have completed processing and reached 'Released', 'Funded', or 'Rejected' states.

• Invoicing Scoping (getUserConcernedWorkRequestIds):  Admin and Accounting personnel can view all client invoices and accounts receivable aging reports within their active entity. Managerial and staff users can only view invoices linked to work requests they have permission to view. Standalone retainer invoices or firm overhead invoices without a linked work request are strictly invisible to non-accounting staff.

6. Two-Phase Pending Approvals & Four-Eyes Principle Matrix

To prevent unauthorized state corruption, fraudulent disbursements, or uncoordinated client commitments, structural modifications are gated by a two-phase staging mechanism backed by the 'pending_changes' table and enforced via backend/src/modules/admin/pendingApprovalsController.js.

6.1 Staged Mutation Lifecycle

1. Submission & Staging:  When a non-admin user creates or edits a critical record, the payload is serialized into JSON and inserted into 'pending_changes' with status 'pending'. The live production table remains unmodified.

2. Review & Verification:  Authorized reviewers inspect the visual side-by-side diff between the current database state and proposedData in the Admin/Submissions portal.

3. Atomic Execution:  An approver triggers the 'pending_change_approve' PostgreSQL RPC, which atomically transitions the status to 'approved' and executes the underlying table mutation under an ACID database transaction.

4. Mandatory Rejection Reason:  If rejected, the reviewer must provide a mandatory written reason. Status flips to 'rejected', and the submitter is notified via their 'My Submissions' tab.

6.2 Segregation of Duties & Self-Approval Prevention

The system strictly enforces the Four-Eyes Principle: no user (with the sole exception of the Administrator) can approve their own submission. The frontend check 'pc.submittedBy === Auth.user.id' completely disables approval buttons, and the backend returns 403 Forbidden if a submitter attempts to self-approve. Furthermore, approval authority is segregated by domain:

• Workflow Task Gate:  Only Managers and Admins can approve tasks added to work requests by staff.

• Financial Records Gate:  Only Accounting staff and Admins can approve invoice creation, line item edits, or disbursement expense filings.

• Executive Governance Gate:  Only Admins can approve new work requests submitted by Managers, phase routing transitions, client profile edits, and transmittal releases.

8.1 Production Hardening & Operational Security Notes

1. Credential Security:  Default passwords ('password123') must be changed immediately upon production deployment via PATCH /v1/me/password. The database enforces bcrypt password hashing via Supabase Auth GoTrue service.

2. Cache Invalidation Vulnerability:  In-memory user profiles are cached for 300 seconds (5 minutes) in backend/src/middleware/auth.js. When an administrator deactivates an account (is_active = false) or demotes a role, the profileCache must be explicitly pruned or the Node process restarted to ensure immediate token revocation.

3. Monorepo Documentation Policy:  In accordance with project operational governance, this document is created solely as an internal reference asset within the /docs directory and must remain strictly uncommitted in git revision control.
